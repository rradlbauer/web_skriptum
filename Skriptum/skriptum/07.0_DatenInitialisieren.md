# 07.0 – Daten initialisieren

## Warum Beispieldaten?

Für die **Demonstration** und das **Testen** der Anwendung braucht es vordefinierte Daten. Ohne Beispieldaten wäre die Anwendung beim Start leer – man könnte sich nicht einloggen und keine Funktionen testen.

Das Clinical Diary verwendet die Klasse `DataInitializer`, die beim Start der Anwendung automatisch **Demo-Patienten, Demo-Ärzte, Health Records und ICD-10-Codes** erstellt.

---

## DataInitializer – Die Struktur

```java
package com.clinicaldiary.config;

import com.clinicaldiary.entity.*;
import com.clinicaldiary.repository.*;
import org.springframework.boot.CommandLineRunner;
import org.springframework.security.crypto.password.PasswordEncoder;
import org.springframework.stereotype.Component;

@Component
public class DataInitializer implements CommandLineRunner {

    private final PatientRepository patientRepo;
    private final DoctorRepository doctorRepo;
    private final HealthRecordRepository recordRepo;
    // ... weitere Repositories

    public DataInitializer(PatientRepository patientRepo, DoctorRepository doctorRepo,
                           HealthRecordRepository recordRepo, /* ... */) {
        this.patientRepo = patientRepo;
        this.doctorRepo = doctorRepo;
        this.recordRepo = recordRepo;
        // ...
    }

    @Override
    public void run(String... args) {
        // Hier werden alle Beispieldaten erstellt
    }
}
```

### Was bedeutet `CommandLineRunner`?

`CommandLineRunner` ist ein **Spring Boot Interface**, das eine `run()`-Methode definiert. Diese Methode wird **automatisch ausgeführt**, nachdem die Anwendung gestartet ist:

```
Anwendung startet
    ↓
Spring initialisiert alle Beans
    ↓
DataInitializer.run() wird aufgerufen
    ↓
Beispieldaten werden in die Datenbank geschrieben
    ↓
Anwendung ist bereit für Anfragen
```

## Patienten erstellen

```java
Patient patient1 = new Patient();
patient1.setEmail("anna.schmidt@email.at");
patient1.setPassword(passwordEncoder.encode("password123"));
patient1.setSsn("1234567890");
patient1.setFirstName("Anna");
patient1.setLastName("Schmidt");
patient1.setDateOfBirth("1990-05-15");
patientRepo.save(patient1);
```

**Wichtige Punkte:**

| Aspekt | Erklärung |
|--------|-----------|
| `passwordEncoder.encode()` | Passwort wird mit **BCrypt** gehasht – nie im Klartext speichern! |
| `patientRepo.save()` | JPA generiert automatisch den passenden `INSERT`-Befehl |
| `email` | Dient als **Login-Name** (einzigartig) |

Es werden **drei Patienten** erstellt:

| Name | E-Mail | Geburtsdatum |
|------|--------|--------------|
| Anna Schmidt | anna.schmidt@email.at | 1990-05-15 |
| Max Muster | max.muster@email.at | 1985-08-22 |
| Maria Weber | maria.weber@email.at | 1978-12-03 |

## Arzt-Patienten-Zuordnungen

```java
DoctorPatient dp1 = new DoctorPatient();
dp1.setDoctorId(doctor1.getId());
dp1.setPatientId(patient1.getId());
dp1.setAssignedAt("2025-01-15T10:00:00");
doctorPatientRepo.save(dp1);
```

Es werden drei Zuordnungen erstellt:

| Arzt | Patient | Zugewiesen am |
|------|---------|---------------|
| Dr. Tandler | Anna Schmidt | 2025-01-15 |
| Dr. Tandler | Max Muster | 2025-02-01 |
| Dr. Müller | Anna Schmidt | 2025-03-10 |

> **Hinweis:** `doctor1.getId()` gibt die ID zurück, die von JPA nach dem `save()` generiert wurde. Die Zuordnung kann daher nur erstellt werden, nachdem beide Entities gespeichert sind.

## Der Lebenszyklus der Daten

```
Entity erstellen (new Patient())
        ↓
Setter aufrufen (patient.setEmail(...))
        ↓
Repository aufrufen (patientRepo.save(patient))
        ↓
JPA generiert SQL: INSERT INTO PATIENTS (email, password, ...) VALUES (?, ?, ...)
        ↓
H2-Datenbank speichert die Daten
        ↓
ID wird zurückgegeben (patient.getId())
```

---

## H2 In-Memory Datenbank

Die Daten leben **nur solange die Anwendung läuft**:

```
Anwendung starten     → DataInitializer erstellt Daten
Benutzer arbeitet     → Daten werden geändert
Anwendung stoppen     → Alle Daten gehen verloren
Neu starten           → DataInitializer erstellt Daten neu
```

Das ist ideal für die **Entwicklung und das Testen**. Für den Produktiveinsatz würde man eine persistente Datenbank verwenden (PostgreSQL, MySQL).
