# 03.1 – JPA Relationen & Abfragen

## Einführung

In diesem Kapitel analysieren wir, wie das Clinical Diary Projekt **Beziehungen zwischen Entitäten** modelliert. Ihr werdet sehen, dass dieses Projekt einen bewusst anderen Ansatz wählt als die klassischen JPA-Relationen mit `@ManyToOne` und `@OneToMany`.

## Design-Entscheidung: Fremdschlüssel als Long-Felder

### Der klassische Ansatz (was ihr kennt)

In bisherigen Projekten habt ihr wahrscheinlich so gearbeitet:

```java
// Klassischer JPA-Ansatz mit @ManyToOne
@Entity
public class HealthRecord {
    @Id
    private Long id;

    @ManyToOne
    @JoinColumn(name = "patient_id")
    private Patient patient;  // → Direkte Referenz auf Patient-Objekt
}
```

### Der Ansatz in diesem Projekt

```java
// Projekt-Ansatz: Fremdschlüssel als Long
@Entity
public class HealthRecord {
    @Id
    private Long id;

    @Column(nullable = false)
    private Long patientId;  // → Nur die ID, kein Referenz-Objekt
}
```

### Warum dieser Unterschied?

| Aspekt | `@ManyToOne` (klassisch) | `Long` ID (dieses Projekt) |
|--------|-------------------------|---------------------------|
| **Transparenz** | JPA versteckt die FK-Beziehung | Die FK-Beziehung ist **explizit** sichtbar |
| **Komplexität** | Lazy Loading, Fetch-Strategien | Einfach – `findById()` Aufruf |
| **Debugging** | ORM-Probleme schwer nachvollziehbar | Klare SQL-Struktur |
| **Lernziel** | Fortgeschritten | Grundlagen – bewusst einfacher |
| **Performance** | Mögliche N+1-Probleme | Kontrollierter Datenbankzugriff |

> **Für dieses Projekt ist der Long-Ansatz bewusst gewählt**: Er ist einfacher zu verstehen, zu debuggen und zu erklären. In der Praxis würdet ihr oft `@ManyToOne` verwenden.

## Die Zuordnungstabelle: DoctorPatient

Die Beziehung **Arzt ↔ Patient** ist eine **Many-to-Many**-Beziehung: Ein Arzt hat viele Patienten, ein Patient kann viele Ärzte haben.

### Klassischer Ansatz (zum Vergleich)

```java
// Klassisch: Join-Table wird automatisch erstellt
@Entity
public class Doctor {
    @ManyToMany
    @JoinTable(name = "doctor_patient",
        joinColumns = @JoinColumn(name = "doctor_id"),
        inverseJoinColumns = @JoinColumn(name = "patient_id"))
    private Set<Patient> patients;
}
```

### Projekt-Ansatz: Explizite Entität

```java
// Im Projekt: Eigene Entität für die Zuordnung
@Entity
@Table(name = "doctor_patient")
public class DoctorPatient {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(nullable = false)
    private Long doctorId;

    @Column(nullable = false)
    private Long patientId;

    private String assignedAt;  // Wann wurde die Zuordnung erstellt?

    // Getter und Setter...
}
```

**Vorteile dieses Ansatzes:**

1. **Zusätzliche Daten**: `assignedAt` speichert, wann die Zuordnung erstellt wurde
2. **Explizit**: Die Zuordnung ist eine eigene Tabelle mit eigener Logik
3. **Einfach**: Kein `@ManyToMany` mit seinen versteckten Implikationen

### Verwendung im Controller

```java
// Arzt einem Patienten zuweisen
@PostMapping("/me/doctors/{doctorId}")
public ResponseEntity<?> assignDoctor(Authentication auth, @PathVariable Long doctorId) {
    Long patientId = getCurrentPatientId(auth);

    // Prüfen ob Zuordnung bereits existiert
    if (doctorPatientRepo.existsByDoctorIdAndPatientId(doctorId, patientId)) {
        return ResponseEntity.badRequest().body(Map.of("error", "Already assigned"));
    }

    // Neue Zuordnung erstellen
    DoctorPatient dp = new DoctorPatient();
    dp.setDoctorId(doctorId);
    dp.setPatientId(patientId);
    dp.setAssignedAt(LocalDateTime.now().toString());
    doctorPatientRepo.save(dp);

    return ResponseEntity.ok(Map.of("message", "Doctor assigned"));
}
```

## RecordConfirmation – Arzt bestätigt eine Gesundheitsakte

Wenn ein Arzt eine Gesundheitsakte überprüft und bestätigt, wird eine `RecordConfirmation` erstellt:

```
┌──────────────────┐      ┌─────────────────────────┐
│  HealthRecord    │      │  RecordConfirmation     │
│──────────────────│      │─────────────────────────│
│ id: 1            │  ←── │ recordId: 1             │
│ patientId: 1     │      │ doctorId: 1             │
│ category: ILLNESS│      │ doctorName: "T. Tandler"│
│ title: "Cold"    │      │ comment: "Looks good"   │
└──────────────────┘      │ confirmedAt: "2025-..." │
                          └─────────────────────────┘
```

```java
// In DoctorController:
@PostMapping("/records/{recordId}/confirm")
public ResponseEntity<?> confirmRecord(Authentication auth,
                                        @PathVariable Long recordId,
                                        @RequestBody Map<String, String> body) {
    HealthRecord record = recordRepo.findById(recordId).orElseThrow();

    // Prüfen ob Arzt dem Patienten zugeordnet ist
    if (!doctorPatientRepo.existsByDoctorIdAndPatientId(
            getCurrentDoctorId(auth), record.getPatientId())) {
        return ResponseEntity.status(403).body(
            Map.of("error", "Patient not assigned to you"));
    }

    // Prüfen ob bereits bestätigt
    if (confirmationRepo.findByRecordId(recordId).isPresent()) {
        return ResponseEntity.badRequest().body(
            Map.of("error", "Record already confirmed"));
    }

    // Bestätigung erstellen
    RecordConfirmation conf = new RecordConfirmation();
    conf.setRecordId(recordId);
    conf.setDoctorId(doctorId);
    conf.setDoctorName(doctor.getFirstName() + " " + doctor.getLastName());
    conf.setComment(body.get("comment"));
    conf.setConfirmedAt(LocalDateTime.now().toString());
    confirmationRepo.save(conf);

    return ResponseEntity.ok(Map.of("message", "Record confirmed"));
}
```

## RecordIcd10 – ICD-10-Codes zuweisen

Ärzte können Gesundheitsakten mit **ICD-10-Diagnosecodes** versehen:

```
┌──────────────────┐      ┌──────────────────┐
│  HealthRecord    │      │  Icd10Code       │
│──────────────────│      │──────────────────│
│ id: 1            │      │ id: 1            │
│ title: "Cold"    │      │ code: "J00"      │
└──────────────────┘      │ description: ... │
                          └──────────────────┘
           │                        │
           └───────┐   ┌────────────┘
                   ▼   ▼
          ┌─────────────────────┐
          │  RecordIcd10        │
          │─────────────────────│
          │ recordId: 1         │
          │ icd10CodeId: 1      │
          │ icd10Code: "J00"    │
          │ doctorId: 1         │
          │ assignedAt: "..."   │
          └─────────────────────┘
```

> **Hinweis**: `RecordIcd10` speichert die ICD-10-Daten **flach** (`icd10Code`, `icd10Description`), obwohl sie auch in `Icd10Code` stehen. Das ist **Redundanz bewusst** – so muss beim Anzeigen keine JOIN-Query ausgeführt werden.

## Custom @Query Methoden für Joins

Da wir keine `@ManyToOne`/`@OneToMany`-Referenzen verwenden, brauchen wir **eigene Queries** für Verknüpfungen:

### Patienten eines Arztes finden

```java
// In DoctorPatientRepository:
@Query("SELECT dp.patientId FROM DoctorPatient dp WHERE dp.doctorId = :doctorId")
List<Long> findPatientIdsByDoctorId(Long doctorId);
```

```java
// Verwendung im DoctorController:
@GetMapping("/me/patients")
public ResponseEntity<?> getPatients(Authentication auth) {
    // 1. Alle Patienten-IDs für diesen Arzt holen
    List<Long> patientIds = doctorPatientRepo.findPatientIdsByDoctorId(
        getCurrentDoctorId(auth));

    // 2. Patienten-Objekte laden
    return ResponseEntity.ok(patientRepo.findAllById(patientIds)
        .stream().map(p -> {
            Map<String, Object> m = new HashMap<>();
            m.put("id", p.getId());
            m.put("firstName", p.getFirstName());
            m.put("lastName", p.getLastName());
            return m;
        }).collect(Collectors.toList()));
}
```

### Ärzte eines Patienten finden

```java
// In DoctorPatientRepository:
@Query("SELECT dp.doctorId FROM DoctorPatient dp WHERE dp.patientId = :patientId")
List<Long> findDoctorIdsByPatientId(Long patientId);
```

```java
// Verwendung im PatientController:
@GetMapping("/me/doctors")
public ResponseEntity<?> getAssignedDoctors(Authentication auth) {
    List<Long> doctorIds = doctorPatientRepo.findDoctorIdsByPatientId(
        getCurrentPatientId(auth));
    return ResponseEntity.ok(doctorRepo.findAllById(doctorIds));
}
```

## Vergleich: Klassisch vs. Projekt-Ansatz

### Klassischer JPA-Ansatz

```java
@Entity
public class Doctor {
    @ManyToMany
    private Set<Patient> patients;
}

// Abfrage:
Doctor d = doctorRepository.findById(1L).orElseThrow();
Set<Patient> patients = d.getPatients(); // ← Lazy Loading
```

### Projekt-Ansatz

```java
@Entity
public class DoctorPatient {
    private Long doctorId;
    private Long patientId;
}

// Abfrage:
List<Long> ids = doctorPatientRepo.findPatientIdsByDoctorId(1L);
List<Patient> patients = patientRepo.findAllById(ids);
```

| Aspekt | Klassisch | Projekt-Ansatz |
|--------|-----------|----------------|
| **Zeilen Code** | Weniger | Mehr |
| **Lesbarkeit** | Versteckt | Explizit |
| **Debugging** | ORM-Herausforderungen | Klare SQL-Struktur |
| **Flexibilität** | Eingeschränkt | Volle Kontrolle |
| **Lernwert** | Mittel | Hoch |

## Zusammenfassung

- Das Projekt verwendet **Fremdschlüssel als `Long`-Felder** statt JPA-Referenzen
- **DoctorPatient**, **RecordConfirmation** und **RecordIcd10** sind **explizite Zuordnungsentitäten**
- **`@Query`-Methoden** ermöglichen Join-Abfragen ohne ORM-Referenzen
- Der Ansatz ist **transparenter** und **einfacher zu debuggen**
- In der Praxis würdet ihr oft `@ManyToOne`/`@OneToMany` verwenden – versteht aber beide Ansätze
