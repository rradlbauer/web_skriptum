# 04.2 - Security Filter: Der JwtAuthenticationFilter

Im vorherigen Kapitel haben wir gesehen, wie JWT-Tokens erzeugt und validiert werden. Aber **wo** wird die Validierung bei jedem eingehenden Request durchgeführt? Die Antwort: im **JwtAuthenticationFilter**. Dieser Filter ist das Bindeglied zwischen dem HTTP-Request und dem Spring Security-Kontext.

## Was macht der Filter?

Der `JwtAuthenticationFilter` ist eine Klasse, die **vor jedem Request** ausgeführt wird und:

1. Das JWT-Token aus dem `Authorization`-Header liest
2. Das Token validiert
3. Die User-Informationen aus dem Token extrahiert
4. Diese Informationen im **SecurityContextHolder** speichert
5. Den Request an den nächsten Filter / den Controller weiterleitet

## Der vollständige Filter-Code

```java
@Component
public class JwtAuthenticationFilter extends OncePerRequestFilter {

    private final JwtTokenProvider tokenProvider;

    public JwtAuthenticationFilter(JwtTokenProvider tokenProvider) {
        this.tokenProvider = tokenProvider;
    }

    @Override
    protected void doFilterInternal(HttpServletRequest request,
                                    HttpServletResponse response,
                                    FilterChain filterChain)
                                    throws ServletException, IOException {

        // SCHRITT 1: Authorization-Header auslesen
        String header = request.getHeader("Authorization");

        // SCHRITT 2: Prüfen ob "Bearer"-Token vorhanden
        if (header != null && header.startsWith("Bearer ")) {
            String token = header.substring(7);  // "Bearer " entfernen

            // SCHRITT 3: Token validieren
            if (tokenProvider.validateToken(token)) {
                // SCHRITT 4: Claims auslesen
                String email = tokenProvider.getEmailFromToken(token);
                Long userId = tokenProvider.getUserIdFromToken(token);
                String role = tokenProvider.getRoleFromToken(token);

                // SCHRITT 5: Authority erstellen
                var authority = new SimpleGrantedAuthority("ROLE_" + role);

                // SCHRITT 6: Authentication-Objekt erstellen
                var authentication = new UsernamePasswordAuthenticationToken(
                        new UserPrincipal(userId, email, role),  // Principal (User)
                        null,                                     // Credentials (nicht nötig)
                        List.of(authority)                        // Authorities (Rollen)
                );

                // SCHRITT 7: In SecurityContext setzen
                SecurityContextHolder.getContext().setAuthentication(authentication);
            }
        }

        // SCHRITT 8: Weiter zum nächsten Filter / Controller
        filterChain.doFilter(request, response);
    }
}
```

### Schritt-für-Schritt-Erklärung

#### Schritt 1 & 2: Header lesen und prüfen

```java
String header = request.getHeader("Authorization");
if (header != null && header.startsWith("Bearer ")) {
    String token = header.substring(7);
```

Der Client sendet den Token im Format:
```
Authorization: Bearer eyJhbGciOiJIUzUxMiJ9.eyJzdWIi...
```

Wir prüfen, ob der Header existiert und mit `"Bearer "` beginnt. Dann schneiden wir die ersten 7 Zeichen ab, um den reinen Token zu erhalten.

> **Warum "Bearer "?** Das ist ein Standard (RFC 6750). "Bearer" bedeutet "derjenige, der dieses Token vorzeigt, ist der Inhaber der Rechte."

#### Schritt 3: Token validieren

```java
if (tokenProvider.validateToken(token)) {
```

Die `validateToken()`-Methode aus `JwtTokenProvider` prüft:
- Ist die **Signatur** korrekt? (Wurde der Token von unserem Server signiert?)
- Ist der Token **abgelaufen**? (`exp` Claim)
- Ist das Format **gültig**?

Falls die Validierung fehlschlägt, passiert **nichts** – der Filter leitet den Request einfach weiter, ohne Authentication zu setzen. Der User gilt als **nicht eingeloggt**.

#### Schritt 4: Claims extrahieren

```java
String email = tokenProvider.getEmailFromToken(token);
Long userId = tokenProvider.getUserIdFromToken(token);
String role = tokenProvider.getRoleFromToken(token);
```

Wir lesen die drei wichtigsten Werte aus dem JWT-Payload:
- **email**: Die E-Mail-Adresse des Users
- **userId**: Die Datenbank-ID
- **role**: Die Rolle ("PATIENT", "DOCTOR", "SUPERUSER")

#### Schritt 5 & 6: Authentication-Objekt erstellen

```java
var authority = new SimpleGrantedAuthority("ROLE_" + role);
var authentication = new UsernamePasswordAuthenticationToken(
        new UserPrincipal(userId, email, role),
        null,
        List.of(authority)
);
```

`UsernamePasswordAuthenticationToken` ist Spring Securitys Standard-Objekt für Authentifizierungs-Informationen:

| Parameter | Bedeutung |
|---|---|
| `principal` | Das UserPrincipal-Objekt (unsere User-Daten) |
| `credentials` | `null` – Passwort wird hier nicht gebraucht (haben ja JWT) |
| `authorities` | Liste der Berechtigungen (z.B. `ROLE_PATIENT`) |

Die Rolle wird mit dem Präfix `ROLE_` versehen – das ist eine Konvention von Spring Security.

#### Schritt 7: SecurityContext setzen

```java
SecurityContextHolder.getContext().setAuthentication(authentication);
```

Der **SecurityContextHolder** ist ein statischer Speicher, der für die Dauer eines Requests die Authentifizierungs-Informationen hält. Ab jetzt "weiß" Spring Security, **wer** den Request gesendet hat.

#### Schritt 8: Weiterleiten

```java
filterChain.doFilter(request, response);
```

Der Request wird an den nächsten Filter in der Kette weitergeleitet – oder am Ende an den Controller.

## Der UserPrincipal

```java
public class UserPrincipal {
    private final Long userId;
    private final String email;
    private final String role;

    public UserPrincipal(Long userId, String email, String role) {
        this.userId = userId;
        this.email = email;
        this.role = role;
    }

    public Long getUserId() { return userId; }
    public String getEmail() { return email; }
    public String getRole() { return role; }
}
```

`UserPrincipal` ist eine **einfache DTO-Klasse** (Data Transfer Object), die die drei wichtigsten User-Informationen hält. Sie wird als `principal` im `UsernamePasswordAuthenticationToken` gespeichert und kann später im Controller ausgelesen werden.

> **Hinweis:** Dieser Name "Principal" kommt aus der Java-Security-Welt und bedeutet "die Identität eines Benutzers".

## Zugriff auf den User im Controller

Wenn der Filter seine Arbeit getan hat, kann jeder Controller auf den eingeloggten User zugreifen:

```java
// Variante 1: Authentication-Parameter
@GetMapping("/patient/diary")
public ResponseEntity<?> getMyDiary(Authentication auth) {
    UserPrincipal user = (UserPrincipal) auth.getPrincipal();
    Long patientId = user.getUserId();
    String email = user.getEmail();
    // ...
}

// Variante 2: SecurityContextHolder direkt
@GetMapping("/patient/diary")
public ResponseEntity<?> getMyDiary() {
    Authentication auth = SecurityContextHolder.getContext().getAuthentication();
    UserPrincipal user = (UserPrincipal) auth.getPrincipal();
    // ...
}
```

Die erste Variante (mit `Authentication`-Parameter) ist **vorzuziehen**, da Spring Security den Parameter automatisch befüllt.

## Der vollständige Ablauf

```
┌─────────────────────────────────────────────────────────────────┐
│  CLIENT (Browser / Frontend)                                    │
│                                                                 │
│  localStorage.getItem('token') → "eyJhbGciOi..."              │
│  Request: GET /api/patient/1/diary                              │
│  Header: Authorization: Bearer eyJhbGciOi...                   │
└──────────────────────────────┬──────────────────────────────────┘
                               │
                               ▼
┌─────────────────────────────────────────────────────────────────┐
│  SPRING SECURITY FILTER CHAIN                                   │
│                                                                 │
│  ┌──────────────────────────────────────────────────────────┐   │
│  │  JwtAuthenticationFilter                                 │   │
│  │                                                          │   │
│  │  1. Header "Authorization" lesen                        │   │
│  │  2. "Bearer " entfernen → Token                         │   │
│  │  3. validateToken(token) → true/false                   │   │
│  │  4. Claims extrahieren (email, userId, role)            │   │
│  │  5. UsernamePasswordAuthenticationToken erstellen        │   │
│  │  6. SecurityContextHolder.setAuthentication(...)        │   │
│  └──────────────────────────────────────────────────────────┘   │
│                               │                                  │
│                               ▼                                  │
│  ┌──────────────────────────────────────────────────────────┐   │
│  │  Controller (z.B. PatientController)                     │   │
│  │                                                          │   │
│  │  Authentication auth wird injected                      │   │
│  │  UserPrincipal user = (UserPrincipal) auth.getPrincipal()│   │
│  │  → userId = 1, email = "patient@example.com"           │   │
│  └──────────────────────────────────────────────────────────┘   │
└─────────────────────────────────────────────────────────────────┘
```

## Was passiert ohne Token?

Wenn ein Request **keinen** `Authorization`-Header enthält:
1. Der Filter überspringt den `if`-Block
2. Kein Authentication-Objekt wird gesetzt
3. `SecurityContextHolder` bleibt leer
4. Spring Security erkennt: User ist **nicht authentifiziert**
5. Der Request wird mit **401 Unauthorized** abgelehnt (für geschützte Endpoints)
