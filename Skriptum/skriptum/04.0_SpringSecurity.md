# 04.0 - Spring Security

Bisher haben wir in unserem Clinical Diary Backend REST-APIs entwickelt, die von jedem Client ohne Einschränkungen aufgerufen werden konnten. Das ist für ein Produktionsprojekt natürlich nicht akzeptabel – jeder Nutzer sollte sich erst **authentifizieren** (identifizieren) und nur auf seine eigenen Daten zugreifen können. Genau hier kommt **Spring Security** ins Spiel.

## Warum brauchen wir ein Sicherheitsframework?

Ohne explizite Sicherheitskonfiguration gilt für REST-APIs:

| Problem | Folge |
|---------|-------|
| Jeder kann `/api/patients/me/records` aufrufen | Patient A sieht die Daten von Patient B |
| Keine Passwort-Prüfung beim Login | Jeder kann sich als jeder ausgeben |
| Keine Rollen-Unterscheidung | Patienten können Arzt-Funktionen nutzen |
| Kein Schutz vor Angriffen | CSRF, Session-Hijacking, etc. |

Ein **Sicherheitsframework** wie Spring Security löst diese Probleme, indem es jeden eingehenden Request prüft, **bevor** er bei unserem Controller ankommt.

## Was ist Spring Security?

**Spring Security** ist das Standard-Framework für Sicherheit in Spring-Anwendungen. Es bietet:

- **Authentication** (Authentifizierung): *Wer bist du?* – Überprüfung von Benutzername/Passwort, Token, etc.
- **Authorization** (Autorisierung): *Was darfst du?* – Rollenbasierte Zugriffskontrolle (z.B. darf dieser Arzt diesen Patienteneintrag lesen?)
- **Schutz** vor gängigen Angriffen: CSRF, Session-Fixation, Clickjacking, etc.

> **Wichtig:** Authentication und Authorization sind zwei verschiedene Konzepte!
> - **Authentication** = Identität feststellen (Login)
> - **Authorization** = Zugriffsberechtigung prüfen (Rolle, Rechte)

## Grundlegende Konzepte von Spring Security

Bevor wir in den Code schauen, müssen wir drei Konzepte verstehen, die das Fundament von Spring Security bilden:

### 1. Die Security Filter Chain

Spring Security arbeitet mit einer **Kette von Filtern** (Filter Chain). Jeder HTTP-Request muss diese Kette durchlaufen, **bevor** er beim Controller ankommt:

```
Client → [Filter 1] → [Filter 2] → ... → [Filter N] → Controller
```

Jeder Filter hat eine spezifische Aufgabe:
- **CorsFilter**: Prüft Cross-Origin-Anfragen
- **CsrfFilter**: Schützt vor CSRF-Angriffen (bei JWT deaktiviert)
- **AuthenticationFilter**: Prüft, ob der User eingeloggt ist
- **AuthorizationFilter**: Prüft, ob der User die Berechtigung hat

> **Analogie:** Stell dir einen Club mit einem Türsteher vor. Jeder Gast (Request) muss am Türsteher vorbeikommen, bevor er zur Bar (Controller) gelangt. Der Türsteher prüft den Ausweis (Token) und entscheidet, ob der Gast reindarf.

In unserem Projekt fügen wir einen **eigenen Filter** hinzu – den `JwtAuthenticationFilter` – der JWT-Tokens validiert. Dieser wird **vor** den Standard-Filtern von Spring Security eingefügt.

### 2. Der Security Context

Der **Security Context** ist ein Speicher, der für die Dauer eines Requests die Informationen über den eingeloggten User hält:

```
SecurityContextHolder
    └── SecurityContext
            └── Authentication
                    ├── Principal (UserPrincipal: userId, email, role)
                    ├── Credentials (null – Passwort nicht nötig bei JWT)
                    └── Authorities (Rollen: ROLE_PATIENT, ROLE_DOCTOR, etc.)
```

Sobald ein Filter den User authentifiziert hat, speichert er die Informationen im Security Context. Von da an kann jeder Controller auf diese Informationen zugreifen – zum Beispiel über den `Authentication`-Parameter:

```java
@GetMapping("/me/records")
public ResponseEntity<?> getRecords(Authentication auth) {
    // Spring Security füllt 'auth' automatisch mit den Daten aus dem Security Context
    UserPrincipal user = (UserPrincipal) auth.getPrincipal();
    Long userId = user.getUserId();
    // ...
}
```

> **Das ist der Grund, warum `Authentication auth` in unseren Controller-Methoden steht** (siehe Kapitel 02.1): Spring Security injiziert automatisch die Informationen des eingeloggten Users.

### 3. Was macht Spring Security automatisch?

Bevor wir Spring Security anpassen, schauen wir uns an, was es **standardmäßig** bereits tut:

| Funktion | Standard-Verhalten | Unser Projekt |
|----------|-------------------|---------------|
| Login-Formular | Eigenes Formular (`/login`) | **Deaktiviert** – wir verwenden JWT |
| HTTP Basic Auth | Browser-Popup | **Deaktiviert** – wir verwenden JWT |
| Sessions | Server speichert Session | **Deaktiviert** – stateless mit JWT |
| CSRF-Schutz | aktiviert | **Deaktiviert** – sicher mit JWT |
| Passwort-Speicherung | Klartext | Wir verwenden **BCrypt** |
| URL-Schutz | Alle Endpoints geschützt | Wir machen **einige Endpoints öffentlich** |

Wir müssen also nur die Teile anpassen, die in unserem JWT-basierten Projekt anders funktionieren als der Standard.

## Session-basiert vs. JWT-basiert

In einer typischen Thymeleaf-Anwendung haben wir bisher session-basiert gearbeitet:

```java
// Bisher (Thymeleaf-Ansatz):
// 1. User loggt sich ein → Session wird auf dem Server gespeichert
// 2. Server speichert User-Info im HttpSession-Objekt
// 3. Bei jedem Request prüft der Server die Session
```

Beim **Clinical Diary** verwenden wir jedoch **JWT (JSON Web Token)** für eine **stateless** (zustandsfreie) Authentifizierung:

```
// JWT-Ansatz:
// 1. User loggt sich ein → Server generiert ein JWT-Token
// 2. Client speichert das Token (localStorage)
// 3. Client sendet das Token bei JEDEM Request im Header mit
// 4. Server validiert das Token bei jedem Request selbstständig
```

Der Unterschied: **Keine Session wird auf dem Server gespeichert.** Der Server speichert keinen Zustand über eingeloggte Benutzer – jedes Request bringt seine eigenen Credentials mit.

## Die SecurityConfig-Klasse

Jetzt knowen wir die Konzepte und können uns anschauen, wie wir Spring Security für unser JWT-basiertes Projekt konfigurieren. Die gesamte Sicherheitskonfiguration erfolgt in einer einzigen Klasse:

```java
@Configuration
@EnableWebSecurity
public class SecurityConfig {

    private final JwtAuthenticationFilter jwtFilter;

    public SecurityConfig(JwtAuthenticationFilter jwtFilter) {
        this.jwtFilter = jwtFilter;
    }

    @Bean
    public SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
        http
            .cors(cors -> cors.configurationSource(corsConfigurationSource()))
            .csrf(csrf -> csrf.disable())
            .formLogin(form -> form.disable())
            .httpBasic(basic -> basic.disable())
            .sessionManagement(sm -> sm.sessionCreationPolicy(SessionCreationPolicy.STATELESS))
            .authorizeHttpRequests(auth -> auth
                .requestMatchers("/api/auth/**").permitAll()
                .requestMatchers("/h2-console/**").permitAll()
                .requestMatchers("/", "/index.html", "/css/**", "/js/**",
                    "/*.html", "/*.css", "/*.js").permitAll()
                .anyRequest().authenticated()
            )
            .headers(headers -> headers.frameOptions(frame -> frame.disable()))
            .addFilterBefore(jwtFilter, UsernamePasswordAuthenticationFilter.class);

        return http.build();
    }
}
```

Schauen wir uns jede einzelne Zeile an:

### `.cors()` – Cross-Origin Resource Sharing

```java
.cors(cors -> cors.configurationSource(corsConfigurationSource()))
```

**CORS** kontrolliert, welche externen Domains auf unsere API zugreifen dürfen. Da unser Frontend (z.B. auf `localhost:3000`) und unser Backend (auf `localhost:8080`) auf unterschiedlichen Ports laufen, wird ein **Cross-Origin-Request** ausgeführt. Ohne CORS-Konfiguration würde der Browser diese Requests blocken.

### `.csrf().disable()` – CSRF deaktivieren

```java
.csrf(csrf -> csrf.disable())
```

**CSRF (Cross-Site Request Forgery)** ist ein Angriff, bei dem ein böswilliger Server Anfragen an unsere API im Namen eines eingeloggten Users sendet. Bei **REST-APIs mit JWT** ist CSRF allerdings kein Risiko, weil:

- JWT-Tokens werden **nicht automatisch** vom Browser mitgeschickt (wie Cookies)
- Das Token muss **explizit** im `Authorization`-Header gesetzt werden
- Ein externer Server kann diesen Header nicht setzen

Deshalb ist es üblich, CSRF bei JWT-basierten APIs zu **deaktivieren**.

### `.formLogin().disable()` und `.httpBasic().disable()`

```java
.formLogin(form -> form.disable())
.httpBasic(basic -> basic.disable())
```

Spring Security aktiviert standardmäßig ein Login-Formular und HTTP-Basic-Auth. Da wir unser eigenes Login-System mit JWT verwenden, deaktivieren wir beides.

### `.sessionManagement(STATELESS)`

```java
.sessionManagement(sm -> sm.sessionCreationPolicy(SessionCreationPolicy.STATELESS))
```

Dies ist der **kern** unseres Ansatzes: Spring Security soll **keine Sessions** auf dem Server erstellen. Jeder Request muss sich selbst authentifizieren – typischerweise über ein JWT-Token im Header.

### `.authorizeHttpRequests()` – Zugriffsregeln

```java
.authorizeHttpRequests(auth -> auth
    .requestMatchers("/api/auth/**").permitAll()
    .requestMatchers("/h2-console/**").permitAll()
    .requestMatchers("/", "/index.html", "/css/**", "/js/**",
        "/*.html", "/*.css", "/*.js").permitAll()
    .anyRequest().authenticated()
)
```

Hier legen wir fest, welche Endpoints **öffentlich** (`permitAll()`) und welche **geschützt** (`authenticated()`) sind:

| Muster | Bedeutung |
|---|---|
| `/api/auth/**` | Login, Register – **öffentlich** |
| `/h2-console/**` | H2 Datenbank-Konsole – **öffentlich** (nur für Entwicklung!) |
| `/*.html`, `/css/**`, etc. | Statische Dateien – **öffentlich** |
| `.anyRequest().authenticated()` | **Alles andere** erfordert Login |

### `.addFilterBefore()` – JWT-Filter einfügen

```java
.addFilterBefore(jwtFilter, UsernamePasswordAuthenticationFilter.class)
```

Wir fügen unseren **eigenen JWT-Filter** ein, der **vor** dem Standard-Filter von Spring Security ausgeführt wird. Dadurch wird jeder Request zuerst von unserem Filter geprüft, bevor Spring Security seine Standard-Authentifizierung durchführt.

### `.headers().frameOptions().disable()`

```java
.headers(headers -> headers.frameOptions(frame -> frame.disable()))
```

Dies deaktiviert den Schutz gegen **Clickjacking** über Iframes. Ist nötig, damit die H2-Konsole (die in einem iframe läuft) funktioniert. **Achtung:** In Produktion sollte dieser Schutz aktiviert bleiben!

## Passwort-Hashing mit BCrypt

```java
@Bean
public PasswordEncoder passwordEncoder() {
    return new BCryptPasswordEncoder();
}
```

**BCrypt** ist ein Passwort-Hashing-Algorithmus, der Passwörter **sicher** speichert:

```java
// Passwort hashen (bei Registration):
String rawPassword = "meinPasswort123";
String hashedPassword = passwordEncoder.encode(rawPassword);
// Ergebnis: "$2a$10$N9qo8uLOickgx2ZMRZoMye..."
// Jeder Aufruf ergibt einen ANDEREN Hash (dank Salt)!

// Passwort prüfen (bei Login):
boolean matches = passwordEncoder.matches(rawPassword, hashedPassword);
// true → Passwort korrekt
// false → Passwort falsch
```

> **Merke:** Speichere **niemals** Klartext-Passwörter in der Datenbank! BCrypt erzeugt einen Hash, der nicht umkehrbar ist.

## Rollenbasierte Zugriffskontrolle (RBAC)

Im Clinical Diary gibt es drei Rollen:

| Rolle | Beschreibung |
|---|---|
| `PATIENT` | Hat Zugriff auf eigene Tagebucheinträge, Vitals, Medikamente |
| `DOCTOR` | Hat Zugriff auf seine Patienten und deren Einträge |
| `SUPERUSER` | Hat Zugriff auf alles (Admin: `admin@clinicaldiary.at`) |

Die Rollen werden bei der **Registration** bzw. beim **Login** im JWT-Token gespeichert:

```java
// Beim Login in AuthController.java:
String token = jwtTokenProvider.generateToken(patient.getId(), patient.getEmail(), "PATIENT");
```

## Zusammenfassung: Der vollständige Ablauf

```
1. User sendet POST /api/auth/login mit Email + Passwort
2. AuthController prüft Credentials → generiert JWT-Token
3. Client speichert Token im localStorage
4. Client sendet jeden Request mit: Authorization: Bearer <token>
5. JwtAuthenticationFilter liest Token aus dem Header
6. Filter validiert Token und setzt Authentication im SecurityContext
7. Controller kann auf den eingeloggten User zugreifen
```
