# 02.1 Architekturen von Web-Applikationen

In diesem Kapitel betrachten wir, wie Web-Applikationen **aufgebaut** sind (Architektur). Zwei zentrale Konzepte sind **server-side rendering (SSR)** und **client-side rendering (CSR)** sowie die **Single Page Application (SPA)**.

## Die klassische Schichten-Architektur

Eine Web-Applikation ist meist in **Schichten** organisiert. Das kennst du ansatzweise bereits aus dem Java-Skriptum (Spring Boot mit Controller, Service, Repository).

```
┌──────────────────────────────┐  Presentation (HTML/CSS/JS, Controller)
├──────────────────────────────┤  Business-Logik (Service)
├──────────────────────────────┤  Datenzugriff (Repository/JPA)
└──────────────────────────────┘  Datenbank (MySQL)
```

In einer Web-App unterscheiden wir jedoch zusätzlich **Frontend** (Client) und **Backend** (Server):

- **Frontend:** HTML, CSS, JavaScript – läuft im Browser des Anwenders
- **Backend:** Serverlogik (Spring Boot), REST-API, Datenbankzugriff

## Server-side Rendering (SSR)

Beim **server-side rendering** erzeugt der **Server** die fertige HTML-Seite und schickt sie an den Browser. Der Browser zeigt die Seite direkt an.

Ablauf:
1. Der Client sendet einen Request (z. B. `GET /patients`)
2. Der Server führt die Logik aus und erzeugt eine vollständige HTML-Seite
3. Der Server sendet das fertige HTML als Response
4. Der Browser zeigt die Seite an

Beispiel-Technologien: **Thymeleaf** (Spring Boot), das du aus dem Java-Skriptum kennst. Bei jedem Navigieren wird eine **neue Seite** vom Server geladen.

**Vorteile:** gut für SEO, schnelle erste Anzeige, weniger JavaScript nötig.
**Nachteil:** bei jedem Seitenwechsel wird die ganze Seite neu geladen (ein "Blättern"/Neuladen).

## Client-side Rendering (CSR)

Beim **client-side rendering** liefert der Server nur die **Daten** (meist als JSON). Der **Browser** erzeugt die Darstellung mit JavaScript.

Ablauf:
1. Der Client lädt eine Grund-Seite (HTML + JavaScript)
2. Das JavaScript ruft per `fetch` Daten vom Server ab (z. B. `GET /api/patients`)
3. JavaScript baut die Seite im Browser auf (z. B. eine Tabelle)
4. Bei neuen Daten wird nur der betroffene Bereich aktualisiert – **ohne** Seitenneuladen

Beispiel-Technologien: JavaScript mit der `fetch`-API, Frameworks wie React oder Vue.

**Vorteil:** flüssigere Bedienung, keine kompletten Seitenwechsel.
**Nachteil:** erfordert JavaScript, anfangs kommt die Seite "leer" und wird erst nach dem Laden der Daten gefüllt.

## SSR vs. CSR im Vergleich

| Aspekt | SSR | CSR |
|--------|-----|-----|
| Wer erzeugt die Seite? | Server | Browser (Client) |
| Datenformat | fertiges HTML | meist JSON |
| Seitenwechsel | kompletter Neuladen | nur betroffener Teil |
| Beispiele | Thymeleaf | `fetch`-API, React, Vue |

## Single Page Application (SPA)

Eine **Single Page Application (SPA)** ist eine Web-Applikation, die aus **einer einzigen HTML-Seite** besteht. Der Browser lädt die Seite einmal; alle weiteren Inhalte werden per JavaScript nachgeladen und in die Seite eingebaut, ohne dass die Seite neu geladen wird.

Merkmale einer SPA:
- Nur **eine** HTML-Datei (`index.html`)
- Das Rendering passiert **client-seitig** (CSR)
- Daten kommen als JSON über die REST-API
- Navigation erfolgt ohne vollständige Seitenwechsel

Beispiel: eine Patientenverwaltung, bei der die Seite "Patientenliste", "Patient anlegen" und "Details" als Ansichten derselben Seite umgesetzt sind. Der Wechsel zwischen den Ansichten passiert im Browser, Daten werden bei Bedarf vom Server geladen.
